## Project rules
- Catalog data (instruments, brands, models, amps, songs, tones, exercises) lives in the database and is read via query options in `src/lib/catalog.ts`: with the browser Supabase client on Lovable, or through server functions in `src/lib/catalog.functions.ts` when built with `VITE_DATA_BACKEND=local` (Raspberry). Both paths must return the same shapes. Only `scores` accepts public inserts. Why: one source of truth, editable without code changes.
- The user's chosen setup (instrument/brand/model/amp) is kept in localStorage via `src/lib/setup.ts`. Why: no accounts in this app.
- The model picker (`src/routes/strumento.$id.tsx`) shows no instrument photos or drawings: one card per model with colour swatches, a search across all brands, and brand/shape filters. Amps do have a vector drawing each (`src/components/AmpArt.tsx`: layout and colours, no logos), also shown in the Studio. Why: generic shape photos didn't match the real models and retailer photos are copyrighted; the user tried model drawings and prefers the clean list, but wants the amp drawings.
- Album covers come from the iTunes Search API through a server function. Why: avoids CORS and storing copyrighted images.
- The user's progress (favourite songs, songs being learned, exercises done per day) is kept in localStorage via `src/lib/progress.ts`, like the setup. Why: no accounts in this app.
- Music theory (notes, tunings, scales, chord formulas, guitar chord shapes) lives in code in `src/lib/theory.ts`, not in the database. Why: these are fixed rules of music, not editable catalog data. Chord shapes are checked against their formulas.
- Music news comes from the public RSS feeds of Rolling Stone Italia and Rockol through a server function (`src/lib/news.functions.ts`): headline, short summary, the publisher's own preview image (hotlinked, never copied) and a link to the article. Why: avoids CORS; Google News RSS terms allow personal use only.
- Courses (`learning_paths` and `lessons` tables, routes `/corsi` and `/corsi/$pathId`) are catalog data in the database; lessons point to existing exercises, songs and tools. Completed lessons are kept in localStorage via `src/lib/progress.ts` and also count towards the practice log and streak. Why: same rules as the rest of the catalog and progress.
- Security: every production response gets security headers from `src/lib/security-headers.ts` (via `src/server.ts`), including a CSP with a per-request script nonce passed to the router (`src/router.tsx`); static files get theirs from `public/_headers`. No inline scripts or `on*=` HTML attributes. A new external host (API, media, font, iframe) must be added to the CSP, and server functions call external sites only through `fetchExternal` in `src/lib/safe-url.ts` (https, allowed domains, timeout, size limit); external URLs go through `safeHttpsUrl` before reaching `href`/`src`. Why: the project will undergo a vulnerability scan.
- The song page plays Apple's official 30-second preview from the iTunes Search API in the background at low volume (server function `getPreview`), with pause/volume and a link to Apple Music; it pauses when a metronome starts. Why: the user wants to hear the song while choosing it; the audio stays on Apple's servers.
- Favourite artists are kept in `progress.artists` (localStorage). Concerts are search links to ticket sites (`src/lib/concerts.ts`: TicketOne, Ticketmaster, Songkick), with no API and no copied dates. Why: ticket APIs need a key and their dates must stay with the publisher.
- Practice tools (`/base` backing track, `/tastiera` fretboard game, `/sessione` guided session, `/progressi` stats) keep their logic in `src/lib/jam.ts`, `fretgame.ts`, `session.ts` and `progress.ts`, with tests. Progressions are generic chord patterns, not songs. Minutes from sessions, games and the backing track go into the practice log via `addPractice`.
- The app is installable (PWA): `public/manifest.webmanifest`, icons in `public/icons/`, and `public/sw.js`, registered from `src/routes/__root.tsx` in production only. The service worker caches only same-origin pages and static files, never server functions (`/_serverFn`), the database or external media. Why: offline use of the tuner and visited pages without serving stale catalog data.
- Management system (`/gestionale`): reached from a single "Accedi" button in the main nav (`src/components/StaffMenu.tsx`, page `/accedi`, only in the local build); after login it becomes a user menu listing just the sections of that role (`src/components/gestionale/nav.ts`). Why: the user wants fewer links, with extra information depending on the credentials. Staff accounts with roles (`src/lib/staff-roles.ts`: admin, catalogo = editor, lettura = read-only; permissions vedere/catalogo/admin) checked on the server in every server function via `requireStaff` (`src/lib/server/auth.server.ts`); scrypt passwords, httpOnly session cookie, only the token hash stored. It is the database of the app's data: an overview of the tables (rows, size, recent changes) and a generic viewer/editor whitelisted in `src/lib/admin-tables.ts` (read-only for roles without the edit permission), plus trusted online shops (`shops` table: search links with `{q}`, no prices copied). No sales, invoices or warehouse: the user asked to remove them. Every change goes to `audit_log`. These tables are closed to anon/authenticated on Supabase. It only works with a local database (`DATABASE_URL`). Why: the user wants a management area that is just the database where the app's data is saved.
- Self-hosting: the app runs on a Raspberry Pi (Linux server) on the local network with its own PostgreSQL; files and guide in `deploy/raspberry/` (install/update/backup scripts, systemd units), migrations applied by `scripts/db-migrate.mjs`, first admin from `scripts/crea-utente.mjs`. New migrations must also run on plain PostgreSQL 15 (no Supabase-only features beyond the anon/authenticated/service_role roles). Why: the user wants it as a server on a Raspberry.
